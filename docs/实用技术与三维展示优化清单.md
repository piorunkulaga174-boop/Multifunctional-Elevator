## 现状与实测依据

现有系统是一台电梯的离散时间步仿真，每步代表 1 秒。`scene3d.py` 使用 Tkinter Canvas 斜投影，人物和轿厢是绘制的图形；它已经把绘图层与仿真层分开，这是继续升级的良好基础。窗口每约 80 毫秒重绘一次，位置仍来自离散的仿真步；这不等于连续运动的真实 3D 场景。

| 检查 | 结果 | 对后续工作的意义 |
|---|---|---|
| 原有单元测试 | 实际发现并通过 52 项 | 可以作为现有规则的回归基线，README 的 51 项数量需更新 |
| 原有压力脚本 | 3 个场景通过 | 证明这些脚本的断言通过，不能扩展为所有场景或真实设备的可靠性证明 |
| 种子 42 到 51，普通与全功能各运行一次 | 总乘客平均分别为 90.1 和 98.8 | 全功能组额外生成行人，且行人目标抽样共用主随机数流；现有完成量差异不能直接解释为效率提升 |
| 同一批 10 次全功能运行 | 10 次均出现重复乘客编号 | 普通客流和行人分别分配编号，接入 3D 前需统一，否则人物对象映射可能冲突 |
| 同一时刻连续调用负重更新 3 次 | 超载时长计数增加 3 | 时长当前随更新调用次数增加，应与仿真时间推进分离 |
| 楼层数 1 和 2，持续 100 秒、到达概率 1 | 均可触发随机范围异常 | 需校验输入并处理无法生成中间楼层往返的情形 |

审查日志在 `.local-audit/baseline-unittest.txt`、`.local-audit/baseline-stress.txt`，独立探查数据在 `.local-audit/probe-baseline.json`，复现脚本为 `.local-audit/probe_baseline.py`。这些本地审查文件已通过 `.git/info/exclude` 排除，避免混入后续提交。

## 三维软件与渲染方案

Blender 适合成为模型、材质、骨骼动画、镜头与最终出片的主工具。官方支持 glTF 等交换格式，也提供 Eevee 和 Cycles 渲染。建议把 `.blend` 作为资产源文件，`.glb` 作为实时展示的交付格式，仿真轨迹单独保存。[Blender 管线](https://www.blender.org/features/pipeline/)、[渲染功能](https://www.blender.org/features/rendering/)。

| 方案 | 适用目标 | 主要收益 | 主要代价 | 建议 |
|---|---|---|---|---|
| Python 仿真加 Blender 轨迹导入 | 演示片、答辩、技术特写、可编辑镜头 | 材质、反射、光照和后期空间大，Python 易于生成关键帧 | 更改场景后需重新仿真或导入；成片无法临场改参数 | 第一阶段优先 |
| Blender 资产加 Three.js 展示 | 浏览器实时操作、共享演示、点击楼层与人物 | 易于组合图表、控制面板和三维视图 | 需要本地服务与前端开发；需处理导出材质差异 | 交互阶段首选 |
| Blender 资产加 Godot | 桌面漫游、复杂人物行为、完整三维应用 | 场景编辑器和 3D 节点体系完整 | 多一套项目、通信和打包流程 | 若强调游戏式漫游可选 |
| 继续增强 Tkinter 斜投影 | 零额外依赖的简易教学版 | 改动成本低 | 写实画质与空间交互提升有限 | 保留为兼容入口 |

Three.js 提供模型加载、PBR 材质、骨骼动画混合与自由观察镜头；Godot 有完整的 3D 工作区和场景节点。上述取舍是针对本项目规模和现有 Python 核心的建议，并非三者的性能测试排名。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)、[MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html)、[AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html)、[OrbitControls](https://threejs.org/docs/pages/OrbitControls.html)、[Godot 三维介绍](https://docs.godotengine.org/en/stable/tutorials/3d/introduction_to_3d.html)。

推荐共用数据流程：

```text
场景配置和预生成的客流
          ↓
Python 仿真核心与调度策略
          ↓
带时间戳的事件、状态快照和运动轨迹
          ├→ Blender 导入脚本 → Eevee 预览 → Cycles 最终渲染
          └→ 本地展示接口 → Three.js 或 Godot 实时展示
```

仿真核心决定人员是否上梯、开关门、到站和告警；展示端根据时间戳播放。切换镜头、降低画质、跳到某个重放时刻都不应改变统计结果。人物上下梯耗时若会影响调度，必须在核心建模，不能只在画面里增加动作。

优先级中，P0 是写实展示与实验可信度的前置工作，P1 是近期适合增加的功能，P2 是后续扩展。成本为相对工作量，不是工期承诺。

| 优先级 | 技术 | 项目内的具体做法与用途 | 成本 | 验收方式 |
|---|---|---|---|---|
| P0 | 统一场景与确定性重放 | 预生成普通乘客、临近行人、放弃时间及目标层；不同策略读取同一份输入，保存种子、配置与版本 | 中 | 同场景重复运行轨迹一致；三组外部输入一致 |
| P0 | 全局唯一人物编号与统一时钟 | 所有人员从一个分配器取得 ID；传感器读取和累计时长分开；补输入范围校验 | 小到中 | 开启行人后无重复 ID；重复读取不增加已过时间 |
| P0 | 状态快照和事件导出 | 输出人物状态、楼层、轿厢位置、门开度、检测状态、事件原因，供 Blender 和实时端共同使用 | 中 | 命令行、重放和渲染的事件时刻一致；无序帧能按时间定位 |
| P1 | 运动学与更细时间步 | 配置楼层高度、最大速度、加减速；门用连续开度；必要时加入限制加加速度的曲线 | 中到大 | 到站误差、运行时间及开门事件可计算复核；改变渲染帧率不改变结果 |
| P1 | 人物通行与排队模型 | 加入走到按钮、候梯、先出后进、穿越门槛和进入轿厢的过程；不同步速、个体体重和行李重量 | 中到大 | 无穿门、无瞬移；载重来自同一批人物；通行时间反映在统计中 |
| P1 | 传感器几何与误差模型 | 雷达由检测区域和人物位置产生观测，配置漏检、误检、延迟、离线；防夹以门区占用/穿越判定 | 中 | 分别记录真实有人、传感器观测与控制决策，统计误取消、迟报和错误重开 |
| P1 | 客流场景库 | 住宅上下班、办公早高峰/午间、医院较慢通行、商场群体到达；先支持时间段、分组到达和起终点矩阵 | 中 | 到达率、方向分布与分组规模可校验；场景可导入导出 |
| P1 | 场景注入与诊断 | 点选“门区被挡”“雷达短时漏检”“称重偏移”“某梯停用”等仿真情节，并展示事件原因 | 中 | 每个情节有明确前置条件、检测结果、状态变化与恢复记录 |
| P1 | 更有解释力的评估面板 | 增加 P50/P95/P99 等待、最长等待、未完成人数、每单位时间完成量、门重开原因；保存配对差值和置信区间 | 中 | 统计包含未完成情形说明；图表可从逐乘客数据重算 |
| P2 | 多电梯群控与策略插件 | 先做 2 到 4 梯，比较最近梯、预计到达时间、分区和等待时间保护；保留当前单梯规则作基线 | 大 | 同一场景配对对比，不提前读取未来需求；检查长等待和无法服务的请求 |
| P2 | 空闲驻停与节能估计 | 比较回首层、就近驻停和需求热点驻停；先统计距离、启停、开门与空载运行 | 中 | 用代理指标比较；只有加入效率、配重和功率参数并校准后才输出能耗估计 |
| P2 | 寻路与人群避让 | 小大厅先用固定通行路线与排队槽位；复杂大厅再加入导航网格和局部避让 | 大 | 人群不穿墙、不互相穿越；电梯作为动态连接单独处理 |

对“更实用”的第一批投入，建议选场景重放、人物通行、传感器误差和统计面板。多梯调度有研究价值，但应在上述基础稳定后做。机器学习调度与预测性维护需要更多训练场景或故障数据，不适合作为当前第一批功能。

## 写实三维展示清单

| 优先级 | 增加内容 | Blender 与实时端的实施要点 | 画面验收 |
|---|---|---|---|
| P1 | 真实比例的建筑与设备 | 明确单位与坐标；建大厅、门套、轿厢、厅门、轿门、井道、导轨及简化配重；门与轿厢分别设可动画节点 | 人物、门宽和轿厢比例协调；设备层级清楚 |
| P1 | 三种展示镜头 | 全楼剖面看调度，单层大厅看候梯与防夹，轿厢内部看载重与出入 | 一键切换，跟随轿厢，不被楼板长期遮挡 |
| P1 | PBR 材质与照明 | 不锈钢门、石材或瓷砖、玻璃、灯带；环境光、局部灯和接触阴影；实时与出片分画质档 | 门板有合适反射，人物不悬浮，场景不过暗 |
| P1 | 人物骨骼与动作 | 待机、走路、按按钮、转身、进出轿厢；状态切换由事件驱动；步速匹配位移 | 无滑步、穿门与上梯瞬移；ID 跟随同一人物 |
| P1 | 门与轿厢的连续动画 | 厅门与轿门分别播放；开度与核心同步，防夹从当前开度反向；运动曲线匹配核心到站时刻 | 不出现画面门已关但人仍穿越的情况 |
| P1 | 可解释的传感器叠层 | 可切换检测扇区、门区、真实人员位置、观测与取消倒计时；正常展示时隐藏教学标线 | 能看清一次取消或重开的原因 |
| P1 | 可编辑的渲染输出 | 保存 `.blend`、外部贴图与轨迹；先做短片段 Eevee 预览，再做 Cycles 出片，推荐先输出图像序列再合成 | 同轨迹不同镜头不改变事件；中断渲染可继续 |
| P2 | 声音与成片包装 | 到站音、门机声、运行声、报警、楼层指示；按仿真事件对齐，支持关闭 | 音画同步，报警和事件对应 |
| P2 | 渲染性能控制 | 楼层构件共享网格、实例化；人物按距离降低细节；限制阴影范围和反射数量 | 定义机型、分辨率与人数后测帧时间和显存，再确定画质档 |

Blender 的高质量程序材质、物理效果和节点动画不保证原样进入 glTF。实时用的材质宜采用金属度/粗糙度 PBR，必要时烘焙纹理；复杂动画先烘焙，再在目标引擎检查。`.blend` 保留完整的后期渲染版本。[Blender glTF 导出说明](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)。重复静态构件可采用 Three.js 的实例化来减少绘制调用；普通 InstancedMesh 不能直接解决骨骼人物的大规模动画成本。[InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)。

## 建议实施顺序

1. **数据基础**：修正编号和计时，统一场景输入，输出可重放轨迹及统计；增加对应回归检查。
2. **Blender 单梯样片**：制作一层大厅和轿厢资产，导入一段正常乘梯与防夹场景；先验证人物、门与时钟一致，再提高画质。
3. **完整展示**：扩展到十层剖面，补大厅/轿厢镜头、材质照明、音效和可编辑 `.blend`；同轨迹渲染多视角短片。
4. **实用场景**：加入个体重量、排队通行、传感器误差、场景预设和诊断面板，验证功能差异。
5. **实时交互**：复用 Blender 资产和轨迹协议，接 Three.js；如果明确需要桌面漫游，再选择 Godot。
6. **研究扩展**：多梯派梯、分区、空闲驻停和能耗估计，每项独立分支与 PR，使用同一场景做配对评估。

第一批 PR 建议拆为“数据与统计修正”“轨迹导出”“Blender 导入与样例场景”。模型和轨迹避免与算法大改混在同一 PR，方便作者逐步审核。

所有功能继续沿用本项目的软件仿真与教学研究范围。写实画面、告警次数和传感器模拟不构成真实设备安全验证。
